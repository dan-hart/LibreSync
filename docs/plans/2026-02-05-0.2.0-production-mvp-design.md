# 0.2.0 production MVP design

## Goal
Ship a production-ready 0.2.0 release for desktop-only targets with a stability-first focus. The release must harden core behavior, provide reliable CLI and AlwaysOn flows, and include Linux systemd service support for the always-on daemon.

## Scope summary
- Rust core, CLI, FFI, always-on daemon, and AlwaysOn desktop app are all bumped to 0.2.0.
- No new adapters or sync semantics are introduced; this release is hardening and polish.
- Linux background behavior is delivered via systemd user service for the daemon.
- macOS and Windows use the AlwaysOn tray app (no OS-level services in 0.2.0).

## Non-goals
- New cloud, relay, or internet-based discovery.
- New data model or CRDT semantics beyond current logical record and file adapters.
- Mobile SDK production readiness.

## Architecture overview
- The Rust core remains the single source of truth for sync protocol, crypto, adapters, and discovery.
- The CLI and AlwaysOn app both dogfood the Engine API.
- The headless always-on daemon uses the same config and state layout as the UI app.
- Linux systemd user service runs the daemon with explicit opt-in auto-accept or auto-approve.

## DX criteria
- Stable API surface and clear integration guides for JSON, SQLite, and logical adapters.
- Predictable conflict resolution and testable behavior for sync flows.
- Consistent diagnostics across CLI, daemon, and AlwaysOn app with actionable error output.

## UX criteria
- Explicit linking and visible trust indicators (fingerprints, last-seen, last-sync).
- E2EE is default and clearly communicated in status and UI.
- Always-on behavior is reliable with clear status and retry indicators.

## Stability gates
- `cargo test` passes for all crates.
- Core tests cover discovery, linking, crypto lifecycle, adapters, and event ordering.
- CLI and daemon integration tests cover link, refresh, fallback addresses, and error paths.
- AlwaysOn UI has smoke coverage for status, manual refresh, and trust flows.
- Linux service template is validated with a documented runbook.

## Workstreams
- Core hardening and error taxonomy alignment.
- CLI and daemon reliability, diagnostics, and recovery behavior.
- AlwaysOn desktop app UX polish for trust and status clarity.
- Linux systemd service packaging and documentation.
- Release docs and MVP checklist updates.

## Testing plan
- Expand unit tests for conflict convergence, adapter merge/load, and crypto lifecycle.
- Add integration tests for linking and refresh flows with fallback addresses.
- Validate daemon config handling and auto-approve safeguards.
- Document a Linux service test runbook and include service template checks.

## Release checklist
- Versions bumped to 0.2.0 across all modules.
- Release notes updated with MVP scope.
- PROGRESS.md updated with 0.2.0 milestone status.
- Linux service instructions validated and documented.
- All tests pass and stability gates are met.

## Risks
- mDNS discovery variability across networks.
- Auto-approve misuse on untrusted networks.
- AlwaysOn UI and daemon divergence if config/state handling drifts.
